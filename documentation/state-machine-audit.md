# State machine audit and decision

Source inspection: 2026-11-08. Applies to the shared Estio/Substo web application, Studio workers/companion, native editor and relay source. This is a source audit, not production acceptance or a claim that textual search can prove every implicit machine.

## Decision

Make transitions explicit **within each existing domain**, incrementally. Keep current persistence, API commands, SQL lease fencing and recovery evidence. Do not add a global workflow engine or mass-convert status strings to database enums. Existing policy modules are the starting point, not a second system.

For each changed workflow, define the current state, command, guard, next state, side effects, retry policy and recovery path in its owning module. Derive available actions and user-facing progress from that same policy. Keep permissions and atomic version/lease checks on the server. A pure transition function cannot replace a transaction.

This aligns UX (truthful progress and a useful next action), DX (one transition owner and focused tests), and AX (structured command outcomes and discoverable contracts). No design guarantees improvement in every circumstance: preserve behavior and verify each slice before expanding.

## Confirmed workflow families and owners

- Identity and access: `lib/auth/`, `lib/locations/`, `lib/team/`, `lib/platform/`. Account/realm, membership, invitations, active tenant, impersonation and offboarding are separate dimensions. Tenant changes must invalidate stale commands; a UI selection is not authority.
- Business onboarding: `lib/onboarding/state.ts`, `screen-state.ts`, and onboarding command services. Overall completion, research batches/runs, topic review, suggested facts, AI availability and disclosure state interact. `reopen` preserves completion history; do not interpret a timestamp alone as current completion. `updateRun` accepts partial patches; inspect its callers and stale-batch protection before narrowing transitions.
- CRM records: property publication/occupancy, prospect dedup/review, conversation lifecycle, deals/offers/documents, tasks/reminders and match campaigns in `prisma/schema.prisma` and their `lib/` owners. Business status, presentation filters and job progress must remain separate.
- Messaging: `lib/whatsapp/status-updates.ts`, `lib/queue/whatsapp-outbound.ts`, `lib/integrations/provider-outbox-enqueue.ts`, `lib/queue/provider-outbox.ts`. Message delivery and outbox execution are distinct machines. Existing monotonic delivery reconciliation is a reusable precedent. Dispatch acceptance is not delivery; uncertain delivery must not silently become a resend.
- Integrations: Google/OAuth connection state, Gmail/contact/calendar sync, webhook dedup and provider outboxes. Connected, authorized, healthy and caught-up are distinct facts. Scope and revoked credentials must remain checked at execution time.
- Viewing sessions: `lib/viewings/sessions/` plus ViewingSession models. Appointment, consent, transport, assignment, transcription, translation, insight and summary states run in parallel; do not flatten them into one session status.
- AI: execution, decisions, runtime/automation queues, suggested responses, learning/proposal review and usage attribution. A completed provider call does not mean its proposal was approved or applied.
- Studio: `lib/studio/` and transactional Studio SQL. Sources/import, extraction, knowledge review, ideas/content revisions, uploads/media, schedules/activation and individual runs are separate lifecycles. `schedule-execution-policy.ts` already checks saved versions and recurring authorization. Keep activation separate from run outcome.
- Studio execution/devices: `lib/studio/worker/queue.ts`, `lib/studio/companion/`. Claim/extend/complete/fail are lease-token fenced SQL operations. Device online/busy/paused/revoked, configuration acknowledgement and provider-command status are separate from job completion.
- Build: `lib/build/contract.ts`, `talk-policy.ts`, `conversations.ts`, delivery and merge services. Proposal/approval/claim/verification/review/merge, planning conversation, execution mirror and external reporting differ. `validLease` and fresh Start provenance are existing contracts. A completed T3 turn does not establish verified, merged or deployed work.
- Scraping/import: scraping runs/stages, credential health, review/import sessions, partial results, dedup and property media ownership. Partial completion needs an explicit recoverable outcome, not generic success.
- Websites/domains: publication and public-domain provisioning jobs. Saved draft, published site, DNS/verification and certificate readiness are independent.
- Relay/egress: `lib/device-tunnel/`, WhatsApp bridge/auth placement/generations, SMS relay and `SIMRelay/`. Desired state, observed health, authentication and session leases differ. Preserve canary expiry and quarantine/relink recovery.
- Native editor: `video-editor/Sources/` includes asset acquisition/availability, analysis jobs, export queue, API event jobs, editor interaction/tool state, playback, undo/journal, agent presence and archive operations. Its coordinator remains the shared command authority; follow its own AGENTS.md before changes.
- UI orchestration: pending/error/success, selection, filters, dialogs, tabs, multi-step forms and realtime hydration throughout `app/` and `components/`. Boolean flags are candidates for impossible combinations, not proof of a bug. Keep genuinely independent dimensions separate; use discriminated unions for mutually exclusive phases.
- Operations: deployment, rollback, worker startup, cron installation and backup/recovery in `scripts/`. These are state machines too. Preserve canonical release ancestry, immutable inputs and server leases.

## Implementation order and acceptance

1. Onboarding: characterize existing command paths and batch/version behavior, then centralize permitted run transitions and derive the visible next action. Cover late results from a prior batch, duplicate commands, reopen and provider failure. This is the recommended first runtime slice, not implemented by this audit.
2. Messaging: document the existing delivery/outbox contracts together; cover out-of-order receipts, timeout after dispatch and retry without duplicate delivery. Preserve monotonic reconciliation and idempotency.
3. Build: expose verified versus reported result through existing policy; test expired leases, replayed Start, preserved-result recovery and merge/deploy boundaries.
4. Studio scheduling and viewing sessions: characterize parallel states before consolidating guards; test stale versions, revoked membership/consent, worker crash and retry.
5. Remaining domains: follow the evidence index, changing one owning service and its consumers at a time.

Each slice needs focused transition tests (including rejected/stale events), integration checks at persistence boundaries, and actual populated/empty/mobile/keyboard acceptance for affected UI. Unknown stored states must remain visible and recoverable; do not coerce them into success. Agent/API outcomes should expose stable codes, current version, allowed next commands and retryability without leaking tenant data. Distinguish retry-safe from retry-after-reconciliation.

## Reproduce and limits

Run `node scripts/audit/state-machines.mjs > /tmp/estio-state-machines.json` from the repository root. It reads tracked source and prints JSON with source locations; no application boot, environment secrets, database access, paid calls or mutations. Historical migration/recovery evidence is labelled separately and must be reconciled with current runtime owners.

The index is heuristic: geographic `state`, relation names, filters and derived fields can match; multiline declarations, computed transitions, nested booleans, dynamic SQL and vendor/native code can be missed. Entries are evidence locations, not one machine each, and do not prove reachable transitions. Line numbers drift; rerun before implementation. Runtime behavior is unchanged by this work.
