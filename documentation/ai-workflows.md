Shared by Estio and Substo. **2026-11-20 local candidate, not deployed.** The serving release remains owned by [current status](current-status.md). No app-wide provider parity or new live acceptance is claimed here. Each app has separate Accounts; each Location owns its settings, content and recorded usage.

## Manual Studio text execution

The shared selector offers **My paired Mac subscription** or **Location OpenAI API key (paid)** for extraction, reviews and briefs. The readiness endpoint reads only the authorized active Location and requesting Account's Macs; it returns reasons and key presence, never secrets. Both apps use these same components/services/functions.

Subscription admission requires the requesting Account's own paired Mac in that app/Location, AI-manager authority, fresh heartbeat, processing On, unpaused, Text work On, selected Codex/Claude, applied Setup, matching advertised handler, correct subscription login, fresh capacity and no reported local block. SQL rechecks admission atomically; local execution rechecks settings, auth and capacity. The subscription auth stays on the Mac, in the native CLI. API-key/Console CLI logins are rejected.

The durable job pins the device, provider, model, config version, workflow, prompt version and immutable snapshot. Changing a request's provider with the same request ID conflicts. Changing Setup, disabling processing or revoking the device cancels queued text jobs. Pausing holds queued work. Once running, a valid result can finish under its original route/lease even if settings subsequently change; revocation/membership removal stops completion. No other Account's device can claim/finish the job. Freshly claimed work is serialized per device.

API admission requires explicit paid consent and a saved Location OpenAI key **before enqueue**; execution decrypts that key and uses the existing budget reservation and metered settlement. No key is copied into a job, prompt, log or browser response. Key presence is not entitlement/quota proof. An unreadable key, insufficient budget or provider rejection remains an explicit execution failure. An explicit single-provider request never switches. A request that follows the Location's order switches only as described in [Ordered fallback chain](#ordered-fallback-chain-2026-11-20-local-candidate): before generation, and onto a paid API only when an admin put it in the order.

Both routes reuse the domain snapshot/result contracts and SQL validators. Stale results are preserved and marked stale; original application/approval protections remain. Subscription results record the actual CLI/model and create no platform-paid API usage row or hold. They are still limited by the user's subscription plan and current capacity. Paid API results retain existing usage/hold/reconciliation behavior. Header totals are recorded estimates, not invoices.

Capacity/local-policy waits happen before generation and can retry. Failed/uncertain native execution, lost completion, or expired execution never resends the same job; repeated Jobs retry attempts are fenced. Start a **new explicitly authorized request** after reviewing uncertainty. Paid uncertain outcomes retain their hold and require the existing manager reconciliation/replacement process. Reusing a request ID finds its existing job, including after response loss; it does not change its provider or generate again.

## Mac video transcription (Gap 1 candidate)

Job kind `studio.video_transcribe`, handler advertised by companion `studio-companion-5`; migration `20261118130000_studio_video_transcription` (additive). Reused from the archived Substo editor (`archive/final-local-state`): `app/transcription.js` flow, `transcribe-local.py` and `extract-frames.py`, now under `scripts/studio-video/`.

- **Entry points.** Pasting a YouTube video in the Library form (explicit `transcribe` flag; background enrichment and "refresh" never transcribe), saving a chosen discovery result, and the source page's "Transcribe on my Mac" button all call `studio_enqueue_video_transcription`. Approved-channel schedules call `studio_enqueue_discovered_video_transcriptions` under the discovery lease fence after the result is saved; search/subscription schedules only record *suggestions*.
- **Admission.** AI-manager authority, same app/Location, the requesting Account's own Mac only (`created_by`), processing On, **Video transcription** toggled On in Setup and applied, handler advertised, tools reported ready. A missing/not-ready Mac is reported (`VT001`-`VT004`), never queued and never routed to an API. An offline/paused Mac still accepts the job, which waits (status shown on the source page). Request keys are idempotent per Location; a second active job for a source is reused; a finished transcript is not re-run by paste/search/discovery.
- **Execution (Mac).** yt-dlp metadata (2-hour and 500 MB limits, no live streams) → bounded audio → Parakeet offline from a private cache → captions fallback. Every subprocess is an argv array with fixed absolute tools, `--ignore-config`, the canonical URL after `--`, a minimal environment, output and time bounds, and abort on lease loss. The timestamped transcript is uploaded in lease-fenced chunks *before* the visual pass; scene detection and OCR then run, frames (≤120, ≤1.5 MB) get ±15 s transcript context and are uploaded to private R2 through short-lived signed PUTs. The server reads each object back and binds it only if digest and size match.
- **Result.** `[HH:MM:SS]` transcript saved on the source (`transcript`, `transcriptOrigin=mac_local`) unless a human transcript exists (kept; Mac transcript stored, `transcript_applied=false`). OCR text becomes source units (`source_units` extraction input). A failed visual pass leaves status `partial` with the transcript intact. Completion is one SQL transaction; any rejected result changes nothing.
- **Relevance gate.** Approved-channel jobs first score the video with the Mac's selected subscription text route (title, description, channel, optional captions excerpt, approved Library titles, approved knowledge statements, profile summary; all treated as untrusted data; prompt `studio.video-relevance.v1`). Structured `{relevant, score, reason, matches}`. Defaults (tunable in `DEFAULT_RELEVANCE_THRESHOLDS`, pinned on each job): score ≥ **70** and `relevant` → transcribe; **40-69** (or high score but `relevant=false`) → suggestion needing owner confirmation; **< 40** → logged as skipped. SQL re-derives the band from the pinned thresholds and rejects a Mac result that disagrees. Scoring failure is a visible failure, never an automatic transcription.
- **Setup.** The Setup toggle is now active. The Mac reports tool names/versions only; the Computer page lists what is missing with exact commands, and `scripts/studio-companion-transcription-setup.sh check|install` creates the isolated Python environment, installs yt-dlp and parakeet-mlx and downloads the model once. ffmpeg/ffprobe/tesseract come from Homebrew (never installed automatically).
- **Verification (local, no providers).** Disposable PostgreSQL 17 (`scripts/test-studio-video-transcription.sh`): admission, cross-app/Location/Account denial, idempotency, offline wait, lease/identity fences, rollback of rejected completion, frame digest binding, partial status, human-transcript preservation, discovery gating bands, suggestions-only, withdrawn consent. TypeScript: handler with fixture subprocesses, argv/limit assertions, actual native CLI input capture for the relevance prompt (contract version + candidate/library/knowledge/profile), device-boundary validators, frame store verification. `extract-frames.py` was run against a real ffmpeg-generated two-slide video with real Tesseract.
- **Not verified.** Real yt-dlp/YouTube access, real Parakeet, a real Codex/Claude relevance call, real R2 upload, and signed-in browser/keyboard/mobile acceptance (paste, offline reconnect, approved-channel auto-run, slides/OCR).

## Ordered fallback chain (2026-11-20, local candidate)

Owner decision. Each Location orders its AI connections once, for example Codex subscription → Claude subscription → hosted Location ChatGPT → OpenAI API → Gemini API. Both apps use the same Location settings; there is no app-specific order. Requests that follow the order take its **first eligible** step; there is no "no fallback" rule any more.

- **Storage.** `aiRouting` in the Location AI settings document (`location.ai`): `{ version: 1, chain: [{ kind, model }], taskDefaults: { <family>: { <kind>: model } } }`. Kinds: `device_codex`, `device_claude`, `chatgpt_subscription`, `openai_key`, `gemini_key`. Families: `text`, `extraction`, `translation`, `summaries`, `research`. A task default beats the step's model, which beats the connection default. Until an admin saves an order, the default is Codex → Claude → hosted ChatGPT, with no paid step. OpenAI and Gemini keys stay in the encrypted Location settings store and can be managed at `/settings/ai`. The monthly cap is the existing Location AI budget, `studio.studio_location_ai_settings`, which the atomic reservation reads. It is surfaced with the order, not copied.
- **Whose subscriptions.** Studio personal steps use the requesting person's own paired Mac. Interactive CRM server text uses the requester's own hosted ChatGPT credential in the Codex slot. Location steps are the hosted Location ChatGPT and the Location API keys. Background work with no requesting person skips personal steps.
- **Eligibility.** A step is skipped when it is not connected, not signed in with a subscription, offline, paused or processing off, at its limit, outside the operation's capability, outside the monthly cap, or (for a model a Mac reported) missing the chosen model. Capability means the route lists the operation in `AI_ROUTED_OPERATIONS` (`lib/ai/workflow-capabilities.ts`), and text subscriptions never take audio, image or vision. The pure decision is `resolveAiRoute` (`lib/ai/routing.ts`), and connection status comes from `assembleLocationAiConnections` (`lib/ai/connections-model.ts`). Statuses are `ready`, `limit_reached` (with a provider-reported reset time when known), `unavailable`, `not_connected` and `offline`.
- **When it switches.** Only before generation starts: admission, a capacity/limit wait, or a provider quota/429 rejection before output. A started run, or one whose outcome is uncertain, is never replayed on another step; the existing replay fences stay authoritative. A paid step runs only when it is in the order, the key is saved and the cap has room. Settlement uses the existing reservation.
- **Recorded.** `studio.studio_jobs.route` and paid `studio.studio_ai_usage.route` hold `{ requested, actual, reason }`, e.g. `"Codex limit reached → Claude"`. The review's `model` and the job payload hold what actually runs. Explicit single-provider requests record requested = actual.
- **Studio text admission (migration `20261120120001_ai_route_chain`).** `p_command.route = { requested, candidates: [{ kind, model, deviceId? }], skipped }`. Studio text kinds are `device_codex`, `device_claude` and `openai_key`. SQL rechecks every candidate atomically: it must be in the saved order, on the requester's own ready Mac, or have the key and cap. A Mac moves from Codex to Claude only when its companion reports `textRouteVersion: 1` (`studio-companion-10`); older companions run only Setup's provider/model. On a `subscription_capacity` wait, the device command moves the job to the next eligible candidate, which can be another provider or the hosted paid path, and returns `retry_scheduled`. With no eligible next step, the original same-route retry applies. Without `route`, the explicit contract is unchanged.
- **Companion (`studio-companion-10`, `textRouteVersion: 1`).** Capability reports include advisory model IDs. Codex uses the installed app-server's `model/list` with a 15-second timeout and reports an empty list on failure. Claude uses curated aliases and full IDs. Listing a model does not prove entitlement. Text runs execute the provider/model admitted by SQL and report a retryable `subscription_capacity` wait when the provider cannot start. SQL can then admit the next candidate. Library summaries, onboarding research and video relevance can walk the leading steps on this Mac in a supplied job route. They stop at a server-side or other-Mac step and return a capacity wait. Jobs without a route keep their existing provider selection.
- **Studio text workflows.** Idea reviews, script briefs, staged creation, video templates, source assistant and Knowledge extraction default to the Location order. The explicit Mac and OpenAI choices remain available with per-request authorization. For an OpenAI step, the hosted structured adapter uses its metered `gpt-6-luna` model. A confirmed rejection, missing key or exhausted budget can requeue to the next eligible Mac before generation starts. Dispatch rechecks that the paid step is still in the saved order. Full-source extraction uses the order for each batch. A separately confirmed retry uses the stopped batch’s actual funding.
- **Other Studio device jobs (migration `20261120120003_studio_device_ai_routes`).** Library summaries, Related video search and scheduled video relevance use the order’s eligible Codex and Claude steps on the requesting Account’s own Mac. They use the operation’s existing result validator and persist the actual provider/model. Video transcription itself uses local tools. An explicit onboarding request can also consider eligible server steps in the same order: hosted Location ChatGPT or OpenAI with search, or Gemini over fetched pages. Typed answers are server-only. Uncertain device outcomes remain terminal.
- **API.** `GET`/`PUT /api/studio/ai-routing` (allowed on both hosts), backed by `getLocationAiRouting` / `saveLocationAiRouting` (`lib/ai/routing-service.ts`). The response is `{ connections, chain, taskDefaults, saved, version, budget, canManage }`. Only the viewer's own Mac subscriptions are listed, and no owner IDs or secrets are returned. Saving needs a Location admin signed in as themselves; `monthlyCap` uses the existing budget command. `resolveLocationAiRoute` and `withStudioTextRoute` are the server entry points that feature code calls before admission.
- **Local verification.** The disposable PostgreSQL suite checks both Mac-to-OpenAI and OpenAI-to-Mac handoffs, eligibility, removal of paid steps before dispatch, uncertain-run fencing, staged creation, full-source admission, and shared CRM and Studio reservations. Companion tests cover provider selection and prompt capture. The installed Codex CLI returned model IDs via `model/list`. Signed-in settings saves and live generation and fallback remain open for release acceptance.

### CRM server routing (Phase F, local candidate)

- **Entry points.** A Location-scoped `callLLM` or `callLLMWithMetadata`, the CRM conversation coordinator, and server onboarding use the Phase A resolver and fallback decision. Dedicated adapters still run Gemini cached drafts and streaming, OpenAI Responses, hosted ChatGPT and onboarding search. Estio-global platform calls use their existing explicit provider configuration. `lib/ai/model-router.ts` is retired.
- **Credentials.** Interactive CRM text can use the authenticated requester's own hosted ChatGPT credential in the Codex slot. The executor verifies Location membership. Background and onboarding server calls use Location credentials. CRM server calls have no paired-Mac executor.
- **Models.** The Location's task-family model takes precedence over the chain step model and migration defaults. A request-specific selection applies only to its own connection kind and preserves the Location's provider order. With no task model, legacy text, extraction, translation, design and draft fields can supply a model for their existing provider. The default order contains subscription steps only. A Location that previously relied on a paid key needs that provider in its saved order and a monthly cap. Audio retains its operation-specific model settings.
- **Paid admission.** Migration `20261120120002_crm_ai_route_budget` reserves each CRM paid attempt in the shared Location ledger under the same row lock as Studio. Admission rechecks the saved chain and monthly settled spend plus active holds. CRM reserves at least $0.01 and uses catalog pricing or the existing Gemini estimates with the prompt size and output limit when that estimate is higher. It settles metered token usage using catalog estimates, retains the reservation amount when pricing or usage is missing, releases confirmed pre-generation rejections, and retains holds for uncertain outcomes. Invoices, provider-side tool charges and historical CRM rows are outside this admission ledger.
- **Switching.** Missing credentials and confirmed pre-generation provider rejections can advance to the next eligible step. Accepted Gemini streams, unstructured hosted CLI failures, timeouts and parse failures stop automatically. The Gemini draft and lead parser do not retry hard-coded alternate models. The server returns a truncated stream result after one generation. The browser surfaces stream loss and waits for a new user request. Background runtime jobs can retry preparation failures before dispatch.
- **Tracing.** Successful requests carry the requested and actual connection and model plus any switch reason. The CRM execution logs, draft and skill traces, feature usage rows, and paid reservation ledger retain those fields. CRM reservation rows are excluded from the Studio usage rollup because CRM feature telemetry has its own reporting.
- **Operation-specific adapters.** Live Assist/realtime, upload and viewing audio, property vision/image generation, and embeddings use their existing modality-specific transports. Feed mapping and listing import retain their direct Gemini structured/multimodal adapters. The Gemini draft cache is part of its chain step.
- **Verification.** Routing and prompt tests cover default and saved chains, migration models, personal and media capability boundaries, metering attribution, and pre-generation versus uncertain failures. The disposable PostgreSQL routing suite verifies CRM and Studio share the cap, rejected attempts release holds, and settlement retains route metadata. Live provider execution and settings UI acceptance remain unverified.

## Runtime instructions: what actually reaches the AI

The executable source is [`lib/ai/workflow-capabilities.ts`](../lib/ai/workflow-capabilities.ts), contract version `ai-workflows.2026-11-20.v5`. It is imported into the build; production does not need `documentation/`, which deployment excludes. This document is for people/contributors and is **not automatically read by a model**.

Bounded operation-relevant instructions are explicitly prepended at:

- shared CRM `callLLM` / `callLLMWithMetadata` (including primary skill execution and shared text consumers; `executeCrmRouteStep` callers prepend it themselves);
- the direct Gemini conversation coordinator;
- the hosted subscription CLI prompt builder;
- onboarding's direct provider prompt boundary;
- Studio structured OpenAI request instructions;
- native Mac generation for summaries, onboarding research, video relevance and the three text workflows (diagnostics remain their fixed check prompt).

The Mac CLI still ignores repository rules and has tools/file execution disabled for ordinary text work. Onboarding research alone requests its restricted web tools. A runtime guide describes supported adapters and known limits; it does not grant tools, authorize a mutation, select a funding source, reveal keys or assert live readiness. Runtime tools, tenant/edition checks, validated input and the actual workflow admission remain authoritative. No reliance on a registry skill being selected or on a model independently reading this file.

## CRM interactive routing boundary

The routing context exists only on the authenticated call stack. Immediate manual jobs persist a boolean `interactiveTextOnly` fence and one-attempt limit, never a personal account, model preference or credential. A background claimant or failed interactive attempt stops without converting to a default/API route; the owner must start a fresh request. The two manual draft actions also stop after an unsuccessful/empty skill attempt rather than invoking the legacy generator a second time. This also prevents automatic replay after uncertain generation. Interactive orchestration reads existing contact insights without invoking the legacy global-key embedding route. Background memory retrieval retains that existing embedding behavior; it is not subscription-backed.

The selected model reaches classification, sentiment, skill planning, post-tool synthesis and high-risk critique as an explicit pick on its own connection kind; the Location order still decides the connection. Skill traces retain requested/actual kind, model, provider, funding and switch reason for the planning and synthesis calls. Existing trace cost estimates do not establish invoice reconciliation or complete metering of every legacy classifier/critic/embedding path. Workflow-specific CRM readiness respects edition and modality; subscription-only eligibility cannot enable transcription, realtime, property images or replay speech. Live Assist's direct Gemini assistant prompt also imports the bundled contract. Undeclared skill tools are blocked before handlers execute, including synthetic availability calls.

## Source assistant (2026-11-19, local candidate)

Mode `source_assist` of the existing `knowledge_extract` text run (migration `20261119140000_studio_source_assistant`, prompt `studio.source-assist.v1`, companion `sourceAssistVersion: 1`). It reuses the explicit funding choice, per-request consent, own-Account Mac admission, leases, replay fence, stale checks and paid reservation/settlement. Admission: location member + (Mac) AI manager; an old companion is refused (`P2016`), never routed elsewhere; one active request per source and Account.

- **Evidence.** The saved transcript (reusing the Mac transcript/OCR units, sampled evenly to at most 60 speech and 12 OCR units, snapshot ≤ 20 kB) or, when there is no transcript, the saved description. Also the owner's current notes and message (≤ 2,000 characters). The snapshot is rebuilt to detect staleness; changed sources are labelled, not silently reused.
- **Result.** Strict JSON: reply, optional note, idea title/concept, related-search phrase, citations (exact quotes of supplied units) and limitations; the requested action decides which proposal must exist. Validated in SQL, the companion and the paid adapter. It cannot be applied as Knowledge.
- **Owner actions.** Save to My notes appends a dated entry to `notes` only (existing record command, version-fenced). Create linked idea uses the existing source-idea command. Related-video search triggers the existing Mac route. Without evidence or with Mac unavailable the assistant states why; "Save as written" and "Draft idea from my words" never call a provider.
- **Verification.** Disposable PostgreSQL (`scripts/test-studio-ai-routing.sh`, needs PostgreSQL 17 and `LC_ALL`): scope, funding, old-companion refusal, replay, other-Account claim, payload bounds, validation, no auto-save/billing, staleness, paid-route isolation and the note command. TypeScript: command/result policy, companion handler with a fake adapter, and a captured OpenAI request. Not verified: a real Codex/Claude/OpenAI call, a signed-in browser, and an updated live companion.


The curated Knowledge review uses `studio.knowledge-extract.v3` for new full-source jobs, with the same bounded, metered batch lifecycle. The selected-evidence idea draft uses `studio.source-assist.selected-idea.v1` on the existing source assistant route. It receives exact quotes already saved in the selected review, and remains a proposal until the author explicitly creates a linked idea. Both require `knowledgeCurationVersion: 1` for subscription admission. [Review and scope](studio-source-knowledge.md#curated-review-and-idea-handoff)

### Stopped extraction batch (migration `20261119180000_studio_knowledge_batch_retry`)

A full-source review keeps every completed batch when one batch stops. The Mac reports a fixed-vocabulary stage with an uncertain failure (`cli_not_ready`, `cli_timeout`, `cli_cancelled`, `cli_failed`, `cli_output_limit`, `result_parse`, `result_validation`, `unknown`); the server stores only that stage name, never CLI output or evidence text, and the companion log records it. Uncertain work is never replayed automatically and the replay fence on the failed job is unchanged. The review offers an explicit `retryBatch` command (`studio_retry_knowledge_outline_batch`): the same account that started the review confirms funding again for its original provider, and it creates one new job for exactly that batch through the existing routed enqueue (current paired-Mac readiness and settings, or a new paid reservation). The stopped batch's review and job stay as evidence but the outline hides them once superseded; a stopped batch can be retried once, and only its latest attempt. Verified by `studio/tests/knowledge-batch-retry-assertions.sql` and `scripts/test-studio-ai-routing.sh`.


## Conversational creation assistant (2026-11-21, local candidate)

Replaces the form-driven staged-creation UI. On `/studio/library/[recordId]` (Create in the Assistant) and `/studio/content/create` one conversation drives concept, hook, script and shoot-plan work; there are no required fields, tabs or stage order. Migration `20261121120000_studio_agent_conversation`, prompt `studio.agent.v1`, companion `studioAgentVersion: 1`, runtime guide `studio_agent` in `lib/ai/workflow-capabilities.ts`.

- **Loop.** Each model call is an ordinary `script_brief` run (snapshot mode `studio_agent`) returning one strict-JSON step: a read tool call or the reply. The server runs the tool, stores the observation in `studio_agent_turns`, and queues the next round on the same stored route and consent (`studio_enqueue_routed_text_run`, so Location order, own-Mac subscription or paid OpenAI keep their admission, leases, funding and replay fences). At most four rounds per owner message; the last must reply. A deterministic request id per (turn, round) makes re-queuing a no-op. A failed or unreadable round closes the turn with an explicit message; nothing is replayed.
- **Advancement.** The origin-checked POST `advance` (`/studio/assistant/agent/api`) advances one step. GET is read-only status. A reload resumes by polling the same turn.
- **Tools (read-only, typed, bounded, tenant-bound).** `search_source`, `read_source`, `list_findings` (approved Knowledge with exact saved quotes), `read_stage`, `search_library` (titles only) and `load_skill`. Source tools reach only sources linked to the draft. Observations are untrusted data. Only items marked `cite` can be cited; proposals citing anything else, tools on the last round, unlisted tools and decisions not quoted from the owner's message are rejected in TypeScript and SQL.
- **Skills.** Fixed bundled procedures (`lib/studio/agent-skills.ts`: `check_claims`, `develop_hook_script`, `plan_shoot`) load on demand via `load_skill`; they add no permission.
- **Plan.** Each reply may carry up to four next steps; the latest is persisted and shown and fed to the next round.
- **State and authority.** History, decisions and plan are scoped to the Account (app + user) and the draft; accepted artifacts live on the shared draft. Nothing is written by the model: **Use** applies one proposal to one stage, fenced to the draft version and the stage text the owner saw, with Undo. No publish, delete, global memory, silent paid fallback or related-video search from the loop (that remains the owner's separate action).
- **Length target (migration `20261122120000_studio_agent_length`).** The approximate runtime is read by the server from the owner's own words (`parseDurationRequest`: "about 90 seconds", "a 3–4 minute video", "make it 2 minutes", "no length limit") and stored as the effective `target_seconds` on each turn; the model cannot set it. Narration is estimated at **150 words per minute**; the target range is ±15% of that word count. Only spoken words count: text in `[square brackets]` is a cue/transition, counted separately. A reply is **close** within ±15%, **short/long** beyond it and **meaningfully** off beyond ±30%; the proposal and the draft show requested versus estimated runtime and never mark a mismatch as a pass. A meaningfully-off Script is measured by the server and sent back to the model **once** (round budget unchanged, `lengthRevision` observation), then shown honestly. A single proposal holds at most **1,200 spoken words (8 minutes) and 9,000 characters**, one Script per reply; longer targets are answered as parts, never truncated. Limits end to end: result JSON ≤ 21,000 bytes (TypeScript) / 22,000 (SQL); companion `maxResultBytes` 23,000; snapshot ≤ 23,000 bytes (the current Script is included to 3,500 characters with its measured size; `read_stage` reads 2,800-character windows by offset); output ≤ 6,000 tokens; stage text ≤ 16,000 characters.
- **Removing a script.** **Remove script…** in the Draft panel asks for confirmation (the command itself requires `confirmClear: true`), empties the Script stage and the canonical `script` together, keeps the old text as the stage's previous value so **Undo last change** restores both, and excludes it from the next round's context. The agent has no destructive tool; asked to delete, it points to this action, and to the Content record's Archived option for a whole draft.
- **Entry and route.** Create always starts a fresh conversation; an explicit `?draft=` (deep link or Resume) reopens that draft and any active turn, and the first view offers Resume versus Start new inline when the source already has a draft. A reopened thread keeps the route its last message used (`turn.provider`, with a visible note for a paid route); a new conversation remembers only the last unpaid route chosen in this browser, scoped to account and Location, and never restores a paid route. Displayed excerpts snap to whole words while staying exact substrings at their real offsets.
- **Contract versions and the native companion.** Prompt `studio.agent.v1` (first release: Scripts to 4,000 characters, no duration target) is frozen byte for byte in `lib/studio/agent-policy-v1.ts`; `studio.agent.v2` adds duration targets and 9,000-character Scripts. The Mac companion bundles its prompts and validators, so a running process cannot gain them from a new snapshot field. New agent rounds are stamped v2 (SQL trigger, from the `scriptLimits` snapshot key) and are dispatched only to a Mac reporting `studioAgentVersion: 2` (`studio_pick_text_device`, plus the explicit-provider guard `P2017`); a round stored under v1 runs on a companion reporting 1 or 2, each using the v1 prompt and validator it was stamped with. A v1-only companion also fails any v2 job at its own `promptVersion` check before any model call. The hosted worker selects the spec by stamped prompt. Hosted OpenAI needs no companion. **Release order:** deploy the web release and migration, then restart the companion from the updated checkout. A companion still on an older version keeps receiving rounds of the newest contract it supports; a restart is what makes it report 3 and receive v3 rounds.
- **Contract 3 and guidance (migration `20261123120000_studio_agent_guidance`).** Prompt `studio.agent.v3` adds creative-priority rules (the owner's current message and stated purpose, then the profile offer when the publisher is the workspace brand, drive the material; earlier drafts and examples are history; explicit structural asks such as "two opening approaches" are followed literally), evidence rules (cite an item only when its text states the claim; otherwise `verify`) and "aim at the middle of the length band". It needs a companion reporting `studioAgentVersion: 3`. v1 and v2 stay frozen byte for byte (`agent-policy-v1.ts`, `agent-policy-v2.ts`, hashes asserted in `agent-contract.test.ts`) and run on a v3 companion with their own prompts. The snapshot builder stamps contract 3 (`contract: 3`) **unless the account's only agent-capable Mac still reports 2**, in which case it keeps stamping v2, so deploying the web release never strands a running companion; v3 rounds are dispatched only to a Mac reporting 3. The model-facing length band is ±7% around the middle (acceptance and display stay ±15%).
- **Duration parsing and one bounded correction (migration `20261124120000_studio_agent_correction`, server only).** `parseDurationRequest` also reads ordinary m:ss ("give me a 1:30 revision", "make it 1:30") when the context is a request: strict seconds 00-59, never after at/from/until/between, around a "mark", before pm/am, as h:mm:ss or as a ratio, and the latest explicit request wins over an earlier descriptive or negated one ("after a 6-minute script, make the revision 1:30"; "I asked for 1:30, not 6 minutes"). A Script outside the displayed ±15% range gets one correction (previously only beyond ±30%, only before the third round): the server measures it, sends the gap back, and the model has a round of its own (rounds stay capped at four, so a correction follows at most two evidence reads and round 4 must reply). The correction is kept only if its Script is closer to the request; if it is no closer, fails, is unreadable, or cannot be queued (for example the snapshot bound), the valid first reply is kept (`studio_agent_keep_original`) and the activity line says so. No prompt or companion change.
- **Saved-script provenance.** Applying a Script stores the request target it was generated for (`stages.Script.targetSeconds`, optional, backward compatible) together with the text; the composer target is separate. Manual edits keep the label (it is the request the script was written for; the measured estimate always shows the real length), `previous` keeps text and target so Undo and Remove/Undo restore both exactly, and scripts without a recorded target are never given one.
- **Resume.** Create always starts fresh. The Resume offer is the latest draft with real work (a saved stage or script, or a completed exchange by this account); a draft with only failed or empty attempts is offered only when nothing better exists; the other drafts remain in the source's Script tab.
- **Compatibility.** Old `script_brief` and `studio.creation.v1` jobs, the hosted dispatcher and older companions are unchanged. A companion without `studioAgentVersion` is refused (`P2017`/`SC001`) before any model call. A script template already pinned to a draft (approved versions only) is passed to the agent as structure-only guidance; there is no template picker or required field in the chat.
- **Verification.** `scripts/test-studio-ai-routing.sh` (PostgreSQL 17) includes `studio/tests/studio-agent-assertions.sql`; `lib/studio/agent.test.ts`, `app/(main)/studio/_components/agent-chat.test.tsx` and `lib/studio/agent.db.test.ts` (the real send/advance/apply service against the disposable cluster with only auth, route resolution and the Mac model stubbed). Not verified: a real Codex/Claude/OpenAI round, the signed-in app, an updated live companion.

## Staged creation (superseded UI, server contract retained)

The manual `script_brief` queue also admits `staged_creation` snapshots using `studio.creation.v1`. The owner confirms direction before choosing a route and authorizing generation. Proposals cover stage suggestions, a selected-span rewrite, or a full-script draft. The same account-scoped Mac subscription and Location OpenAI meter apply. The Mac advertises `stagedCreationVersion: 1`. A separate version-fenced application command applies reviewed output. Literal replacement and undo only edit the record and use neither provider. [Staged creation](studio-staged-creation.md)

### Paired Mac readiness at release

Processing On is permission. Current task readiness also depends on a recent heartbeat, local gates such as free disk, the relevant handler and protocol version, a subscription login and a fresh allowance reading. Devices and the AI connection views explain the same reported local block. A missing allowance reading is unavailable capacity; exhaustion requires a fresh reading. Source Assistant's Location order reports unsupported connections separately, including hosted Location ChatGPT. The read-only readiness snapshot supplements atomic admission. It does not acquire a lease, create a paid hold or permit replay. See the [release canary](studio-readiness-runbook.md#paired-mac-continuity-at-release).


### Native Mac subscription allowance

The companion checks Codex with `codex login status` and Claude Code with `claude auth status`, then checks the required CLI features. A ChatGPT or claude.ai subscription login is required. Account API keys and alternate hosts are excluded from the native process environment. QuotaCell is standalone and has no Estio/Substo runtime role.

Codex allowance is optional telemetry from the documented app-server `account/rateLimits/read` RPC. Claude Code has no supported headless allowance read in this integration. Missing or stale allowance is unknown. A ready, signed-in CLI with unknown or nonzero allowance may attempt work, and the provider enforces its limit. A current zero reading or a confirmed pre-generation rejection can make that provider temporarily unavailable. A cooldown without a provider reset time is not displayed as a verified reset. Studio calls the native CLI, while any overage or credits enabled separately on that subscription are controlled at the provider account.

The native companion reports `nativeSubscriptionVersion: 1` and sets the existing `capacity` bit from native readiness and limit evidence. SQL still requires that bit, the actual workflow and version, ownership, current heartbeat, applied Setup, processing permission, and lease. Legacy companion reports keep their old meaning. Queued jobs keep their selected provider, model and consent. A confirmed pre-generation rejection can advance the stored authorized order. An explicit single-provider request stays on that provider. Invalid output, timeouts, partial output, and uncertain runs are fenced from automatic replay. Hosted Location ChatGPT remains unsupported for Source Assistant.
