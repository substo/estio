4. Run `npx tsx scripts/build-worker.ts --once` to inspect connectivity while paused. Remove `--once` for a 15-second polling loop. On this Mac it is installed as login LaunchAgent `co.estio.build-worker`, currently running with the queue paused. Its plist is `~/Library/LaunchAgents/co.estio.build-worker.plist`; logs are under `~/Library/Logs/Estio/`. No separate scheduler is installed.
5. Resume the queue to import tracked `app`, `components`, and `lib` TypeScript/CSS source and static import dependencies. Inspect is deterministic and makes no model call. A first full scan was verified by the parent against disposable PostgreSQL: 1,518 nodes / 4,974 edges, then unchanged reconciliation returned zero changes. Initial inserts are now batched.
6. **Approve models** in Model profiles. No names, IDs or JSON are typed. The Mac worker reports T3's current model catalog on every poll: current models of enabled T3 provider instances, read from `~/.t3/userdata/model-manifest.json` and `settings.json` with no model call. New releases and newly enabled providers therefore appear automatically as "Not allowed". For each model the owner picks Not allowed / Routine / Hard and whether it may write code; guidance notes (`lib/build/model-guidance.ts`, researched 2026-11-03) suggest a level but never approve anything. The server rejects any enabled model not in the reported catalog. Profile ID is `<provider>.<model>`, quota bucket is the provider subscription, and effort is T3's default (the T3 CLI cannot set it).
7. Create a feature linked to a source/page, curate its approved intent, then propose a bounded assignment. **The owner never picks difficulty or a model.** On propose/revise the server runs `assessDifficulty` (zero-token, deterministic). An implementation is Hard when it has more than 4 files, touches a sensitive area (`prisma/`, `lib/auth`, `app/api/`, middleware, `lib/build/`, `scripts/`, deploy, `.sql`), has more than 20 dependent product-map links, or has more than 5 acceptance criteria. A review is Hard above 10 files or 5 criteria; everything else is Routine. The reason is stored as `spec.routing` and shown on the card. Routing prefers an approved model at that level, then any other approved model. A capacity fallback needs a stopped writer and a different provider bucket. No unapproved model ever runs. The base defaults to the last scanned Git HEAD. Approval binds scope, base, profile policy and affected row revisions. Endpoint is local review only; no commit, push, integration or deployment authority exists.

## Worker and adapter boundary

`POST /api/build/worker` uses bearer auth independently of Clerk; `poll`, `claim`, `heartbeat`, `complete` and `reconcile` are strictly validated and body-limited. Worker capability opt-ins are local configuration. Browser mutations use same-origin requests and the platform gate. The customer server never spawns development shell.

**Executor: T3 Code threads (default since 2026-11-03).** The worker runs `t3 thread start <checkout> - --worktree <approved base> --branch build/<slug>-<hash> --provider --model --json` (prompt on stdin), so dispatch costs no model turn and every assignment is a visible, steerable T3 thread on a real `build/…` branch. It polls `t3 thread show --json` every 10 seconds. `BUILD_T3_CLI` overrides the launcher (default `~/.t3/bin/t3`); `BUILD_EXECUTOR=cli` restores the headless `codex exec` / `claude -p` adapter. T3 Code must be running and the Mac awake. The T3 CLI cannot set effort/fast-mode options, so threads use T3 defaults; the checkpoint records this.

`BUILD_CLI_REVIEW=1` admits read-only review and `BUILD_CLI_IMPLEMENTATION=1` admits code-write work on the Mac. The fence adopts the T3-created worktree with a private ownership receipt (`adoptDelivery`): it must be a linked worktree of the checkout at the approved base on the expected `build/` branch. After the thread is idle the fence verifies explicit-file scope and refuses symlinks, sensitive paths, commits and out-of-scope changes; read-only work must leave zero changed files. This is a post-run fence, not a per-file OS sandbox (T3 threads run with full access). Failures preserve all work. **No independent second reviewer runs** (owner decision 2026-11-03, low-token mode); owner review of the branch/diff is the acceptance gate. A thread that asks a question returns to owner review with "answer in T3". T3 has no CLI interrupt: pause/revoke asks the owner to stop the thread in T3; stop is reported only once T3 shows it idle, otherwise the lease expires into the existing stopped-writer recovery. Retries start a fresh thread and branch; earlier worktrees stay preserved. No merge/deploy is authorized. The worker never passes a browser-supplied shell command. Capacity is detected only from a failed thread whose final provider message is a recognized limit message; there is no invented balance, token budget, paid API fallback or monetary ceiling.

Claims and all mutations serialize using one transaction advisory lock. One active or expired-unreconciled assignment blocks further claims. Leases last 60 seconds; CLI heartbeat runs every 10 seconds. Pause/revoke instruct the worker to stop and preserve checkpoint. Expiry does not prove writer death and never silently reclaims a job. Recovery asks the operator for concrete stopped-writer/checkpoint evidence, resets to proposal, and requires fresh approval.

Confirmed capacity exhaustion records the quota bucket globally with observation time and unknown reset, preserves checkpoint, and considers only enabled, qualified ordered fallbacks in another non-exhausted bucket after the prior process is confirmed stopped. Attempt limits are admission controls, not spend caps. Permission/test/auth/configuration errors are not quota errors. No eligible fallback yields waiting-for-capacity. Owner capacity recheck is explicit through the operator API; no guessed reset clears exhaustion automatically.

## Daily routine and task context

The owner can enable a standing daily read-only review with an enabled standard-quality review profile. The same worker claim path admits at most one stale page per UTC day at the last scanned HEAD, rotating by a persisted node-ID cursor without promoting evidence freshness. A deterministic day key prevents duplicate admission. It asks for up to three evidence-backed improvements and a bounded plan, returns to owner review, and never approves writes from model output. Disabling/replacing the grant or changing profile policy stops its authority. Policy changes require a fresh grant. Last admission and next eligible UTC day/poll are visible. No work runs while the Mac is asleep, queue paused, worker stopped, or CLI review disabled; no separate dispatcher or scheduler is installed.

Claims attach affected briefs, direct incoming/outgoing links with evidence, linked record summaries and shared rule records. Each carries exact record/source/evidence revisions. Context limits are 100 direct links, 50 linked records and 10 shared rules, with explicit omission counts and bounded text. Prompts cap mapped context at 32KB and mark truncation. This context is evidence, never extra task authority; the adapter still inspects actual source.

After deployment, connectivity check: `node --env-file=.env.build-worker.local --import tsx scripts/build-worker.ts --once`. Remove `--once` for the loop. ## Watch list (2026-11-03)

Operator actions `watch` (URL, optional note, screen IDs) and `watch-update` (status, mark seen); the record ID is `ref-<hash of host+path>`, ignoring share query strings. Worker `poll` returns up to 10 checkable references due (unchecked or older than 24h). The worker sends `watch-report` with release tag@commit and a one-line summary; failures keep the previous value and retry after 24h. Unauthenticated GitHub API (60 requests/hour) is ample at 2 calls per repo per day. `admitDaily` prefers a screen linked to a changed, unqueued reference, keeps the normal rotation cursor and marks the reference `queued` so one change admits once. `inspires` links are excluded from difficulty dependents. Tests: `lib/build/watch.test.ts`.

## Feedback on results (2026-11-03)

Operator `accept` takes an optional note; `redo` (from review or failed) requires a note. Notes are appended to `checkpoint.feedback` (last 20). Redo re-approves the same spec and base, bound to the current policy and node revisions (`approval.redo`), and returns the job to approved. On claim the worker marks unsent redo notes `sentAt`. If the job has a prior T3 thread and branch, it runs `t3 thread send <thread> -` with only the notes, waits for a new `latestRunId` (refusing a thread that is still running), then polls as usual. The fence re-adopts the same worktree (existing receipt) and verifies the full diff. Without a prior thread (or with the CLI executor) the notes are appended to a fresh prompt. Real smoke on 2026-11-03: a Haiku thread answered, then a continuation in the same thread returned the new answer; the smoke worktree and branch were removed. Tests: continuation and running-thread refusal in `lib/build/t3.test.ts`.

## Review findings → proposals (2026-11-04)

Read-only prompts end with `proposalInstruction` (`lib/build/contract.ts`): a fenced json block `{"proposals":[...]}` with 0–3 items, so no extra model turn is needed. The worker parses the full result text with `extractProposals`: the last valid block wins, items are validated before capping, and dropped items are counted. On `complete` with outcome review, the server re-validates each draft, rejects unsafe scope paths (`validateDeliveryPath`), and creates an implementation proposal per draft. Each one is keyed `from-<review job>-<n>` (idempotent), uses the current scanned head, is linked to the review's screens, and goes through `routed()`, so difficulty and model are system-decided. Proposals are never approved automatically. A daily (standing-grant) review moves to done; an owner-requested review stays in review. Counts are stored as `proposalsCreated` / `proposalsRejected`.

## Policy auto-approval and How it works tab (2026-11-04)

Operator `auto-approve` sets `BuildControl.worker.autoApprove.mode` (off / record / on). `autoDecide` runs after every `propose` and after each review-created card. In record mode it stores `checkpoint.auto = { mode, wouldApprove, reasons }`. In on mode it approves eligible cards with `approval.actor = "policy"` and `auto: true`, binding the current policy and node revisions. The budget counts auto approvals whose `approval.at` falls on the current UTC day (3). Paused queues still claim nothing. The How it works tab renders `lib/build/factory-guide.ts`, a live setup checklist (worker seen within 2 minutes, approved models, queue, daily review, auto-approval mode switch, watch-list count) and capabilities grouped by status. Test: auto-approval policy in `lib/build/build.test.ts`.

## Screen description drafts (2026-11-04)

The daily review's outcome text appends `screenInstruction`: the model adds a `screen` object (purpose, journey, up to 5 features) to the same fenced json block as its proposals. The worker extracts it with `extractScreen` into `checkpoint.screenDraft`. On review completion the server stores it as `spec.draft` on the single reviewed page node. This does not bump the revision, because a draft is not intent, so approvals stay valid. Operator `draft` confirm sets purpose, journey and intent from the draft, sets coverage confirmed, and upserts feature nodes (`feature-<hash(screen:name)>`) with `contains` edges; discard removes the draft. Daily admission prefers pages whose purpose is still the scanner default and that have no draft waiting, using the rotation cursor. Then come changed watch-list items (which take precedence over everything) and the stale rotation. Test: screen draft extraction in `lib/build/build.test.ts`.

Client-only view (`ForYou` in `workspace.tsx`) and Build's default tab. ## Tasks start from their base even after the checkout moves (2026-11-04)

The worker and `precheck` in `delivery.ts` required the Mac checkout's HEAD to equal a task's approved base, so merging one task (which fast-forwards the checkout) failed every task still queued. Each task runs in its own worktree created from its base, so the checkout now only has to contain the base (`git merge-base --is-ancestor`); merge assist puts the result on the latest release branch. A base outside the checkout's history is still refused. Tested in `delivery.test.ts`.

## Scope by files or folders, no file-count cap (2026-11-04)

The 10-file (planned tasks) and 30-file (approved tasks) caps were arbitrary and break on code split into many small files. A task's scope still lists everything it may change, and the fence still refuses anything else, but there is no count limit (up to 200 entries), and an entry ending in "/" covers every file beneath that folder, including new ones (`validateScopeEntry`, `inScope` in `delivery.ts`). Folders must be at least two levels deep. Size is handled by routing: more than 4 files or any folder makes an implementation Hard, and autopilot never starts folder-wide tasks. The planning agent is told that tasks in one plan start from the same code and can't see each other's changes, and that schema and data changes ship as a migration file or a dry-run script for the owner to apply at deploy. Tested in `delivery.test.ts`.
